# THE BOSS fullstack v1.1 — release notes

Prepared 2026-09-21 from the locally validated v1.0.1 build.

## What changed

- Declared Robinhood Chain Multicall3 at the canonical address `0xcA11bde05977b3631167028862bE2a173976CA11`.
- Enabled viem multicall batching on the main website/backend `publicClient` with a 25 ms batch window. This collapses concurrent `readContract()` bursts from dashboard/deployment reads into far fewer RPC round trips.
- Raised the default `RPC_POLL_MS` from 1.8 seconds to 10 seconds because the public Robinhood RPC is rate-limited.
- Added `pollingInterval: config.RPC_POLL_MS` to the main viem public client.
- Updated production/readiness notes to reflect the successful local typecheck/tests, build, smoke test and live pre-launch UI check completed on 2026-09-15.
- Bumped package version to `1.1.0`.

## Why

The live pre-launch website worked correctly, but the public Robinhood RPC returned HTTP/RPC `Too Many Requests` errors during concurrent dashboard reads. v1.1 reduces that request burst without changing game logic, contracts, fee economics, reporter rules, or launch safety gates.

## Deliberately unchanged

- `OPERATIONS_ENABLED=false`
- `TRADER_ADAPTER_VERIFIED=false`
- `V4_REPORTING_ENABLED=false`
- The frozen `docs/REPORTER_SPEC_V1.4.md`
- Contract addresses and game economics
- Reporter signer `makePublicClient()` behavior; independent signer RPC topology stays untouched for now

## First validation after opening this version

Keep operations disabled and run:

```bash
npm install
npm run check
npm run build
npm run smoke
npm run dev
```

Leave `npm run dev` running for at least one minute. The goal is for the terminal to remain stable without repeated `[broadcast] ... Too Many Requests` errors.

If the public RPC still rate-limits, do not weaken application validation. Set `RPC_HTTP_URL` in `.env` to a dedicated Robinhood Chain RPC provider before production.
